# 00 · 제품 개요

> 스펙 버전 v0.1 (2026-10-24) · 상위 기획: [PLANNING.md](../../PLANNING.md) · 프로토콜: [A2A v1.0](https://github.com/a2aproject/A2A) (최신 릴리스 v1.0.1)

## 한 줄 정의

K뷰티·K의료를 찾는 일본·중국·미국 2030 여성 관광객이 **자기 에이전트**를 만들고, 그 에이전트가 **플랫폼 에이전트**와 **병원 에이전트**들과 A2A로 대화해 시술 조건 정리, 가격 적정성 판정, 병원 매칭, 예약, 사후 기록까지 대행하는 웹서비스.

## 세 개의 축, 세 개의 에이전트

| 축 | 에이전트 | 소유자 | 한 줄 역할 |
| --- | --- | --- | --- |
| 고객 | 고객 에이전트 (Pibu 실장) | 고객 | 고객 편에서 조건을 정리하고, 병원과 대화를 대행하고, 기록을 보관한다 |
| 플랫폼 | 플랫폼 에이전트 | Pibu (우리) | 실제 기록으로 가격·용량 적정성을 판정하고, 맞는 병원을 추천하고, 연결 규칙을 계속 고친다 |
| 병원 | 병원 에이전트 × N | 병원 (초기엔 Pibu 대행) | 가격, 용량, 이벤트, 예약 가능 시간을 답하고 예약을 받는다 |

세 에이전트는 모두 같은 웹서비스 안에서 시작하지만, **서로를 함수로 직접 부르지 않고 A2A 1.0 JSON-RPC로만 대화한다.** 그래야 나중에 병원이 같은 Agent Card를 가져가 직접 운영하거나, 고객이 자기 에이전트를 다른 곳으로 옮길 수 있다.

## 기존 Pibu 기획과의 관계 (통합 결정)

이 스펙은 [PLANNING.md](../../PLANNING.md)의 Pibu를 대체하지 않고 **에이전트 구조를 3축으로 확장**한다. 정본은 이 `docs/spec/` 이고, PLANNING.md는 배경·문제 정의·비즈니스 모델의 정본으로 남는다.

| PLANNING.md (기존) | 이 스펙 (확장) | 변경 이유 |
| --- | --- | --- |
| 상담실장 에이전트 (고객 편) | 고객 에이전트의 대화 얼굴 = "Pibu 실장" | 상담 + 기록 + 대화 대행을 고객 소유 에이전트 하나로 묶음 |
| 오케스트레이터 (플랫폼) | 플랫폼 에이전트 | 단순 전달자가 아니라 판정·추천·규칙 개선의 주체로 격상 |
| 병원 에이전트 (목업) | 병원 에이전트 (A2A 1.0 Agent Card, 대행 → 인수) | 병원이 나중에 카드를 가져가 직접 운영할 수 있게 |
| 한국 여성 시술 트래커 | 고객 에이전트의 "내 시술 기록" 기능 (한국 여성도 고객 에이전트를 가짐) | 같은 기록 스키마로 플랫폼 판정 데이터가 쌓임 |
| 자체 JSON 메시지 (`quote_request`) | A2A 1.0 Message + DataPart (`pibu/*@1` 스키마) | 표준 프로토콜로 상호운용 |
| 타깃 20~50대 | **1차 타깃 2030**, 40~50대는 확장 타깃 | 오너 지시 (2026-10-24) |

## 타깃

- **1차 (최종 고객):** 일본·중국·미국 국적 20~39세 여성 관광객. 짧은 체류(2박 3일 ~ 2주) 안에 피부과 시술을 받으려는 사람.
- **데이터 공급:** 피부과 시술을 꾸준히 받는 한국 20~30대 여성 (PLANNING.md의 트래커 사용자). 같은 고객 에이전트를 쓰고, 기록 공유에 동의하면 플랫폼 판정의 표본이 된다.
- **공급자:** 외국인환자 유치 의료기관으로 등록된 서울 피부과 의원 (강남·신사·압구정·명동 우선).

## 핵심 원칙

1. **에이전트끼리는 A2A로만 말한다.** 같은 서버 안에 있어도 내부 함수 호출로 우회하지 않는다. (근거: 병원 인수·고객 이식 가능성이 제품의 약속이다)
2. **고객 데이터는 고객 에이전트 저장소에 있다.** 플랫폼은 고객이 동의한 필드만 A2A 메시지로 받는다. 코드 수준에서 플랫폼 모듈은 고객 저장소를 import 하지 못한다. ([09-architecture.md](09-architecture.md) 모듈 경계)
3. **후기는 병원이 아니라 플랫폼으로 간다.** 병원은 개별 후기를 보지 못하고 집계(n ≥ 5)만 본다.
4. **판정은 실제 결제 기록으로 한다.** 병원 광고가가 아니라 고객이 실제로 낸 금액·받은 용량이 기준이다. 표본이 부족하면 "판정 불가"라고 말한다.
5. **진단하지 않는다.** 에이전트는 의료 판단(적응증, 금기 판단)을 하지 않는다. 안전 정보는 수집해 병원에 전달만 한다. ([08-compliance.md](08-compliance.md))
6. **AI는 Claude만 쓴다.** (해커톤 규칙, README.md)

## 용어

| 용어 | 뜻 |
| --- | --- |
| Agent Card | A2A 1.0의 에이전트 자기소개 JSON. 이름, 엔드포인트(`supportedInterfaces`), 스킬, 인증 방식을 담는다 |
| 스킬 (skill) | Agent Card에 선언된, 다른 에이전트가 요청할 수 있는 능력. 이 스펙의 스킬 id는 `customer.*`, `platform.*`, `clinic.*` 형식 |
| 대행 운영 (proxy-operated) | 병원이 아직 직접 운영하지 않아, Pibu가 병원 문자·공개 정보로 병원 에이전트를 대신 운영하는 상태 |
| 인수 (handover) | 병원이 대행 중인 같은 Agent Card를 넘겨받아 직접 운영하는 것 |
| 요청 (request) | 고객 한마디("리주란 받고 싶어")를 조건으로 정리한 `pibu/procedure-request@1` |
| 판정 (verdict) | 견적 하나에 대해 플랫폼이 내린 가격·용량 적정성 결과 `pibu/fairness-verdict@1` (여러 견적을 묶으면 `pibu/fairness-verdict-list@1`) |
| 결과 (outcome) | 시술 후 고객이 남기는 실결제·실용량·만족도 기록 `pibu/outcome@1` |
| 연결 규칙 (routing rule) | "이 병원엔 보내지 말자", "이런 고객은 이 지역으로" 같은 매칭 규칙 |
| 추천 토큰 (referral token) | 플랫폼이 매칭 때 발급하는 서명 토큰. 병원 에이전트는 이 토큰이 있는 요청만 받는다 (유치 실적 귀속) |
