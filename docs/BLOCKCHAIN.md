# PibooK에서 블록체인은 어디에 쓰이나 (발표용 쉬운 설명)

> 발표 자료를 만드는 사람을 위한 문서다. 블록체인을 몰라도 읽을 수 있게 썼다.
> 기술 상세(API, 스키마, 회로)는 [INTEGRATION.md](INTEGRATION.md), 스펙 근거는 `docs/spec`의 "ZK 확장" 표기를 본다.
> 기준일: 2026-10-24

## 한 줄 요약

**내 시술 기록은 내 폰에 두고, 블록체인에는 "이 기록이 진짜"라는 지문만 올린다. 병원에는 차트 대신 "조건을 만족한다"는 증명만 보낸다.**

## 1. 어떤 문제를 푸나

외국인 의료관광객이 한국 병원에서 혜택을 받으려면 지금은 이런 일이 생긴다.

| 문제 | 지금 | PibooK |
| --- | --- | --- |
| 혜택을 받으려면 과거를 다 보여줘야 한다 | "2회차 할인" 받으려면 어느 병원에서 언제 몇 번 받았는지 차트를 보여준다 | "리쥬란 1회 받았음"만 증명한다. 병원·날짜는 안 보인다 |
| 병원은 고객 말을 믿기 어렵다 | 자기 신고, 캡처는 조작할 수 있다 | 병원이 확인한 기록만 블록체인에 지문이 남는다. 조작하면 지문이 안 맞는다 |
| 후기를 믿기 어렵다 | 시술 안 받은 사람도 후기를 쓴다 | 실제 방문한 사람만, 방문 1번에 1번, 익명으로 쓴다 |

시술 이력은 개인정보 보호법상 민감정보다. 한곳(회사 서버)에 모아 두면 유출됐을 때 피해가 크다. 그래서 원본은 고객 기기에만 두는 구조를 택했다 ([08-compliance.md](spec/08-compliance.md) 5절).

## 2. 비유로 이해하기

| 기술 용어 | 쉬운 비유 |
| --- | --- |
| 블록체인 | 누구나 볼 수 있고 아무도 고칠 수 없는 **공증 장부**. 단, 장부에는 내용이 아니라 지문만 적는다 |
| 해시 (지문) | 차트 내용을 요약한 짧은 숫자. 차트가 한 글자만 바뀌어도 완전히 다른 숫자가 된다 |
| 영지식 증명 (ZK) | **봉투를 열지 않고** 봉투 안 내용이 조건을 만족한다는 걸 확인시키는 기술. 술집에서 신분증 전체 대신 "성인 맞음"만 보여주는 것과 같다 |
| 가명 | 장부에 적히는 이름 대신의 번호. 실명·여권과 연결되지 않는다 |
| 기록 지갑 | 고객 폰에 있는 내 차트 원본. 어떤 메시지로도 밖에 나가지 않는다 |

## 3. 블록체인이 쓰이는 세 곳

### 3-1. 기록 공증: 병원이 확인한 시술은 아무도 고칠 수 없다

```
시술 완료 (병원 확인)
   → 내 폰의 차트에 1줄 추가
   → 새 지문을 블록체인 장부에 기록
   → 장부: "가명 #A, 기록 v2, 지문 0x8f3c..."  (병원·시술·금액은 없음)
```

- 블록체인의 장부 프로그램(스마트 컨트랙트)이 직접 검사한다: **"이전 차트 + 오늘 날짜 기록 정확히 1건"일 때만** 받아준다.
- 그래서 지난 날짜로 끼워 넣기, 기록 지우기, 병원 이름 바꿔치기가 안 된다. **PibooK 운영자도 마음대로 못 고친다.** 규칙이 코드로 체인에 있기 때문이다.
- 장부에 올리는 일은 PibooK이 대신 한다 (수수료도 PibooK이 낸다). 그래서 병원 주소도 장부에 남지 않는다.
- 화면: 내 기록에 **"병원 확인 · 체인 기록 v1"**. 내가 직접 적은 기록은 **"직접 입력 · 증명에 쓰이지 않음"**으로 구분된다.

### 3-2. 차트 대신 증명으로 혜택 받기

병원이 이벤트에 조건을 걸면, 내 에이전트가 **내 폰 안에서** 조건에 맞는지 먼저 확인하고, 맞을 때만 증명을 만들어 견적 요청에 붙인다.

| 병원 이벤트 (데모) | 내가 증명하는 문장 | 병원이 알게 되는 것 |
| --- | --- | --- |
| 민트 "첫 방문 1cc 이벤트" (99,000원) | "민트 기록 0건" | 이 사람은 민트 첫 방문이다 |
| 서울글로우 "리쥬란 2회차 패키지 10%" | "리쥬란 기록 정확히 1건" | 리쥬란 2회차 차례다. **어디서 언제 받았는지는 모른다** |
| 한빛 "리쥬란 이어서 2회차 10%" | "한빛에서 리쥬란 정확히 1건" | 우리 병원에서 1회 받은 고객이다 |

- 병원은 받은 증명을 **블록체인의 지문과 대조해** 검증한다. PibooK 서버를 믿을 필요가 없다.
- 통과하면 이벤트가 + **"조건 충족 증명됨"** 라벨. 실패하거나 증명이 없으면 정가 견적.
- 내 에이전트는 조건이 안 맞는 병원에는 증명을 보내지도 않는다. "증명 실패" 자체가 정보(예: 이 사람은 우리 병원에 와 봤다)가 되기 때문이다.
- 데모 장면 예: 린(중국)은 한빛에서 리쥬란 1회를 받았다. 리쥬란을 다시 요청하면 서울글로우 2회차 패키지와 한빛 이어서 2회차가 **증명만으로** 경쟁한다. 한빛 첫 방문 할인은 받을 수 없다 (이미 와 봤으니까).

### 3-3. 진짜 방문자만 쓰는 익명 후기

```
체인에 기록된 방문 1건 → 후기 티켓 1장 → 익명 후기 1번 (Semaphore)
```

- 블록체인에 기록된 방문이 후기 자격이 된다. 티켓 1장으로 1번만 쓸 수 있다.
- 익명이다. 같은 병원·시술 후기 작성자가 **3명 이상** 모여야 공개한다 (한 명뿐이면 누가 썼는지 짐작할 수 있으니까).
- 보상은 없다 (의료법 광고 규제, [08-compliance.md](spec/08-compliance.md) 3절).
- 후기 글 자체는 블록체인에 올리지 않는다. 블록체인은 "이 사람이 실제로 방문했다"는 자격을 보증하는 역할이다.
- 화면: 병원 비교 화면에 **"피북 사용자 1,240명 · 검증 후기 18건 평점 4.6"** (데모용 가상 통계).

## 4. 무엇이 블록체인에 올라가고, 무엇이 안 올라가나

| 블록체인에 올라감 (누구나 볼 수 있음) | 절대 안 올라감 |
| --- | --- |
| 가명 번호 | 이름, 여권, 국적 |
| 차트 지문 (해시) | 병원 이름 |
| 몇 번째 기록인지 (버전) | 시술 이름, 용량, 금액 |
| 기록된 날 (일 단위) | 후기 글 |
| 거래 번호 (tx) | 병원 주소 (PibooK이 대신 제출) |

차트 원본은 고객의 기록 지갑에만 있다. 병원에는 "조건 충족 여부"만 간다.

## 5. 왜 그냥 데이터베이스가 아니라 블록체인인가 (Q&A 대비)

1. **병원이 PibooK을 믿지 않아도 된다.** 병원은 공개 장부를 직접 읽어 검증한다. 중개 플랫폼의 말을 믿을 필요가 없다.
2. **PibooK도 기록을 몰래 고칠 수 없다.** "오늘 날짜로 1건 추가"만 허용하는 규칙이 컨트랙트 코드로 박혀 있다. 일반 DB라면 운영자가 고칠 수 있다.
3. **민감정보를 한곳에 모으지 않는다.** PibooK 서버가 털려도 차트 원본이 없다. 장부에는 지문만 있다.
4. **기록이 고객 것이다.** 고객 데이터는 고객 에이전트 쪽에 둔다는 제품 원칙([00-overview.md](spec/00-overview.md) 원칙 2)을 기록 수준까지 지킨다. 지갑과 공개 장부만 있으면 PibooK 밖에서도 증명할 수 있다.

| 브라우저에서 증명 만들기 → 병원 검증 | `/demo/wallet` | 동작. 증명 약 3초, 첫 증명은 엔진 로딩 포함 7~10초. **인터넷 필요** |
| 내 기록의 출처 라벨, 비교 화면의 "조건 충족 증명됨"·방문 수·후기 | `/[locale]/records`, `/[locale]/requests/[id]` | 화면 있음 |
| 병원 에이전트가 견적 요청에 붙은 증명을 검증하고 이벤트가 적용 | 병원 에이전트 `clinic.quote` | 연결됨 |
| 고객 에이전트가 견적 요청에 증명을 자동으로 붙이기 | 고객 에이전트 | 진행 중 (A2A 작업과 함께) |

발표 전 확인: 증명 생성·검증·장부 기록은 ZK 데모 서버(glowpass)가 켜진 **데모 맥**에서만 성공한다. 페르소나 차트 원본이 그 맥에만 있기 때문이다 ([INTEGRATION.md](INTEGRATION.md) 1절).
